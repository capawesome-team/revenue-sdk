Webhooks are the only trustworthy source of billing truth: the redirect after checkout can be closed,
retried, or forged, but a signed webhook cannot. `revenue-sdk` ships two standalone helpers per provider
— `verifyWebhook` and `parseWebhookEvent` — that take a Web-standard `Request` and need no client.

## Verify, then parse

Always in that order. `parseWebhookEvent` does **not** verify anything; it will happily parse a forged
payload.

```ts
import { parseWebhookEvent, verifyWebhook } from 'revenue-sdk/stripe';

export async function POST(request: Request): Promise<Response> {
  const headers = request.headers;
  const body = await request.text();

  const valid = await verifyWebhook({ headers, body, secret: process.env.STRIPE_WEBHOOK_SECRET! });
  if (!valid) {
    return new Response('invalid signature', { status: 401 });
  }

  const event = await parseWebhookEvent({ headers, body });
  // ...
  return new Response(null, { status: 204 });
}
```

Both helpers accept either shape:

<TypeTable
  type={{
    request: { type: 'Request', required: false, description: 'A Web-standard Request. Provide this or headers + body.' },
    headers: { type: 'Headers | Record<string, string>', required: false, description: 'Request headers, when you pass the body separately. Names are matched case-insensitively.' },
    body: { type: 'string', required: false, description: 'The raw request body — required with headers.' },
    secret: { type: 'string', description: 'The endpoint signing secret. verifyWebhook only.' },
  }}
/>

`verifyWebhook` returns `false` — it never throws — for a missing header, a stale timestamp, a malformed
secret, or a mismatched signature. Comparisons are constant-time.

## The raw-body rule

Signatures are computed over the **exact bytes** the provider sent. Any re-serialization (parsing JSON
and stringifying it again, a body-parser middleware, a proxy that reformats) breaks verification.

Read the body once with `await request.text()` and pass that same string to both helpers:

```ts
const body = await request.text(); // once
await verifyWebhook({ headers: request.headers, body, secret });
await parseWebhookEvent({ headers: request.headers, body });
```

Passing `{ request }` also works — the helpers clone the request internally — but reading the text once
is cheaper and makes the raw body available for logging and de-duplication.

:::warning
In Express and other Node frameworks, mount a raw-body parser on the webhook route
(`express.raw({ type: '*/*' })`) or the JSON middleware will consume and reshape the payload before you
can verify it.
:::

## Signature schemes per provider

You never have to implement these — `verifyWebhook` handles each transparently — but knowing which
secret goes where saves a lot of debugging:

| Provider          | Header(s)                            | Signed payload             | Key derivation                                       | Digest                                    |
| ----------------- | ------------------------------------ | -------------------------- | ---------------------------------------------------- | ----------------------------------------- |
| **Polar**         | `webhook-id`, `webhook-timestamp`, `webhook-signature` | `{id}.{ts}.{body}` | secret **verbatim, including `whsec_`** (UTF-8) | base64, any `v1,` part               |
| **Dodo Payments** | same (Standard Webhooks)             | `{id}.{ts}.{body}`         | **strip `whsec_`, then base64-decode** into key bytes | base64, any `v1,` part                   |
| **Stripe**        | `stripe-signature`                   | `{t}.{body}`               | secret verbatim, including `whsec_`                   | lowercase hex, any `v1=` (`v0=` ignored) |
| **Paddle**        | `paddle-signature` (`ts=…;h1=…`)     | `{ts}:{body}`              | secret verbatim                                       | lowercase hex, any `h1=`                  |
| **Lemon Squeezy** | `x-signature`                        | body only (no timestamp)   | secret verbatim                                       | hex, compared case-insensitively          |

:::note
Polar and Dodo Payments both advertise "Standard Webhooks", yet they derive the HMAC key **differently**.
Polar's own SDK base64-encodes the raw secret before handing it to the reference library, which cancels
out to using the secret verbatim; Dodo Payments uses the library's strict behavior, where `whsec_` is
stripped and the remainder base64-decoded. Copying one implementation to the other silently fails every
signature — `revenue-sdk` implements each exactly.
:::

Polar, Dodo Payments, Stripe, and Paddle deliveries carry a timestamp and are rejected outside a
**300-second** tolerance, which bounds replay attacks. Lemon Squeezy sends no timestamp, so replay
protection has to come from de-duplication — see [Idempotency](#idempotency).

If you are implementing verification by hand rather than using these helpers, the blog post on
[verifying webhook signatures across all five providers](/blog/verify-billing-webhook-signatures) walks
through each scheme with working code.

## Normalized events

`parseWebhookEvent` maps the provider payload onto a small closed set:

```ts
type WebhookEventType =
  | 'subscription.created'
  | 'subscription.updated'
  | 'subscription.canceled'
  | 'order.paid'
  | 'checkout.completed'
  | 'license.issued'
  | 'unknown';
```

<TypeTable
  type={{
    type: { type: 'WebhookEventType', description: 'The normalized event type.' },
    providerType: { type: 'string', description: "The provider's original event type string, always preserved." },
    idempotencyKey: { type: 'string', description: 'Provider-namespaced dedupe key (<provider>:<id>). Always set, stable across retries and dashboard replays.' },
    subscriptionChange: { type: 'SubscriptionChange', required: false, description: 'Which lifecycle transition the provider named, when it named one. Only ever set on subscription.updated.' },
    createdAt: { type: 'Date', required: false, description: "When the event occurred, from the provider's envelope. Absent on Lemon Squeezy, which sends none." },
    subscription: { type: 'Subscription', required: false, description: 'Set on subscription.* events.' },
    order: { type: 'Order', required: false, description: 'Set on order.paid. Fully mapped — including status, createdAt, and refundStatus.' },
    checkout: { type: 'Checkout', required: false, description: 'Set on checkout.completed (and on not-yet-complete checkout events, which report unknown).' },
    licenseKeyId: { type: 'string', required: false, description: 'Which key a license.issued event refers to. Always set on that event, even when licenseKey is not.' },
    licenseKey: { type: 'LicenseKey', required: false, description: 'The issued key. Absent on Polar, which sends only a masked form — fetch it with licenseKeys.get.' },
    raw: { type: 'unknown', description: 'The untouched provider envelope.' },
  }}
/>

`createdAt` comes from the envelope's own field — Polar and Dodo Payments `timestamp`, Stripe `created`,
Paddle `occurred_at` — and never from the `webhook-timestamp` header, which is the delivery *attempt*
time and moves on every retry. Lemon Squeezy sends neither, so it is `undefined` there.

### What each type means

- **`subscription.created`** — a new subscription exists. Dodo Payments has no such event; its first
  signal arrives as `subscription.updated`, so always upsert rather than insert.
- **`subscription.updated`** — anything changed: activation, renewal, plan change, pause, resume,
  past-due, **and a scheduled cancellation**. This is the workhorse.
- **`subscription.canceled`** — **terminal only**. The subscription has actually ended.
- **`order.paid`** — money was received, **including renewals**. It fires **once per payment**: on Lemon
  Squeezy it covers both `order_created` (first payment) and `subscription_payment_success` (renewals),
  since renewals never emit an order — but the *first* subscription payment raises both, so the invoice
  half of it (`billing_reason: 'initial'`) stays `unknown`. The attached `Order` carries `status`,
  `createdAt`, and `refundStatus`, and its `id` is the same identifier `client.orders.get` takes — see
  [Orders](/docs/concepts/orders) for reading history back.
- **`checkout.completed`** — a checkout was paid. Only Polar and Stripe expose a checkout event the SDK
  can confirm as paid.
- **`license.issued`** — a license key was issued to a customer. Polar, Lemon Squeezy, and Dodo Payments
  only; `licenseKeyId` is always set, `licenseKey` only where the provider sends the key itself. Nothing
  else about a key's lifetime is normalized — see
  [License keys](/docs/concepts/license-keys#getting-notified).
- **`unknown`** — everything else. Never an error.

:::warning
**A scheduled cancellation arrives as `subscription.updated`, not `subscription.canceled`.** Providers
disagree loudly here: Polar emits `subscription.canceled` when a cancellation is merely *scheduled* and
`subscription.revoked` when it takes effect; Paddle emits `subscription.updated` for the schedule and
`subscription.canceled` on the effective date. `revenue-sdk` normalizes both into
`subscription.updated` (with `cancelAtPeriodEnd: true`) followed later by `subscription.canceled`. Read
`event.subscription.cancelAtPeriodEnd`, never the provider's event name.
:::

### The transition the provider named

Alongside `type`, an event reports which lifecycle transition the provider's own event string named —
and leaves the field `undefined` where the provider names none:

```ts
type SubscriptionChange = 'cancel_scheduled' | 'past_due' | 'paused' | 'resumed' | 'uncanceled';
```

This is a **sibling field, not extra `WebhookEventType` members.** The union above still has exactly
those seven members, so a `switch` written before `subscriptionChange` existed keeps compiling and keeps
routing the same events; reading the new field is opt-in.

It is derived **only from the provider's event string, never from payload state** — `cancelAtPeriodEnd`
stays `true` for the rest of the period, so a payload-derived transition would re-report a fresh
"cancellation scheduled" on every later event. Transitions are edges; payload fields are levels.
Coverage is therefore uneven by design (no provider names every transition, and Stripe and Dodo Payments
name almost none) — the per-provider matrix and the three traps it encodes are in
[the webhook events reference](/docs/reference/webhook-events#subscription-changes).

### Unknown events never throw

Provider event catalogs grow. Anything outside the mapped set comes back as
`{ type: 'unknown', providerType, raw }` so a new provider event can never crash your endpoint. The one
case that *does* throw is an unparseable body — a `RevenueError` with code `validation`.

```ts
switch (event.type) {
  case 'subscription.created':
  case 'subscription.canceled':
    await upsertSubscription(event.subscription!);
    break;
  case 'subscription.updated':
    await upsertSubscription(event.subscription!);
    // Opt-in: react to the transition, where the provider named one.
    if (event.subscriptionChange === 'past_due') {
      await warnAboutFailedPayment(event.subscription!);
    }
    break;
  case 'order.paid':
    await recordPayment(event.order!);
    break;
  case 'checkout.completed':
    await fulfill(event.checkout!);
    break;
  case 'license.issued':
    await recordLicenseKey(event.licenseKeyId!, event.licenseKey);
    break;
  default:
    // 'unknown' — log providerType and move on.
    break;
}
```

The full per-provider event matrix lives in
[the webhook events reference](/docs/reference/webhook-events).

## Routing a shared endpoint

`detectWebhookProvider` — exported from the package root — identifies the sender of a delivery so one
endpoint can serve several providers:

```ts
import { detectWebhookProvider, type ProviderName } from 'revenue-sdk';
import * as polar from 'revenue-sdk/polar';
import * as stripe from 'revenue-sdk/stripe';

type WebhookHelpers = Pick<typeof polar, 'verifyWebhook' | 'parseWebhookEvent'>;
const handlers: Partial<Record<ProviderName, WebhookHelpers>> = { polar, stripe };

export async function POST(request: Request): Promise<Response> {
  const headers = request.headers;
  const body = await request.text();

  const provider = await detectWebhookProvider({ headers, body });
  const helpers = provider === undefined ? undefined : handlers[provider];
  if (helpers === undefined) {
    return new Response('unknown sender', { status: 400 });
  }

  const secret = secretFor(provider);
  if (!(await helpers.verifyWebhook({ headers, body, secret }))) {
    return new Response('invalid signature', { status: 401 });
  }

  const event = await helpers.parseWebhookEvent({ headers, body });
  // ...
  return new Response(null, { status: 204 });
}
```

Detection is header-based: `stripe-signature` → Stripe, `paddle-signature` → Paddle, `x-signature` →
Lemon Squeezy. Polar and Dodo Payments share the Standard Webhooks headers, so the JSON body is
inspected for `business_id` (present only on Dodo Payments) — which is why the helper is async.

:::warning
`detectWebhookProvider` is **routing, not authentication.** Headers are attacker-controlled. Always call
the detected provider's `verifyWebhook` before acting on anything.
:::

## A full Cloudflare Worker handler

```ts
import { parseWebhookEvent, verifyWebhook } from 'revenue-sdk/polar';

interface Env {
  POLAR_WEBHOOK_SECRET: string;
  PROCESSED: KVNamespace;
}

export default {
  async fetch(request: Request, env: Env): Promise<Response> {
    if (request.method !== 'POST') {
      return new Response('method not allowed', { status: 405 });
    }

    const headers = request.headers;
    const body = await request.text();

    if (!(await verifyWebhook({ headers, body, secret: env.POLAR_WEBHOOK_SECRET }))) {
      return new Response('invalid signature', { status: 401 });
    }

    const event = await parseWebhookEvent({ headers, body });
    if ((await env.PROCESSED.get(event.idempotencyKey)) !== null) {
      return new Response(null, { status: 204 }); // already handled
    }

    switch (event.type) {
      case 'subscription.created':
      case 'subscription.updated':
      case 'subscription.canceled':
        await upsertSubscription(event.subscription!);
        break;
      case 'order.paid':
        await recordPayment(event.order!);
        break;
    }

    await env.PROCESSED.put(event.idempotencyKey, '1', { expirationTtl: 60 * 60 * 24 * 3 });
    return new Response(null, { status: 204 });
  },
};
```

## Idempotency

Every provider retries deliveries, and several send overlapping events for one state change. Assume
**at-least-once, out-of-order** delivery:

1. **Dedupe on `event.idempotencyKey`.** Every parsed event carries one — required, never empty, and
   stable across the provider's retries and dashboard replays. Store it with a TTL and drop repeats:

   ```ts
   const event = await parseWebhookEvent({ headers, body });
   if ((await kv.get(event.idempotencyKey)) !== null) {
     return new Response(null, { status: 204 });
   }
   ```

2. **Upsert, never insert.** Key subscription state on `event.subscription.id`. Reordered events then
   converge instead of conflicting.
3. **Ignore stale writes.** Compare against a monotonic field (the provider's `updated_at` in `raw`, or
   `currentPeriodEnd`) and skip anything older than what you have stored.
4. **Return 2xx fast.** Acknowledge within a couple of seconds and move slow work off the request — see
   [the webhook handler guide](/docs/guides/webhook-handler).

### Where the key comes from

The key is `<provider>:<id>`, namespaced because `detectWebhookProvider` makes one endpoint for several
providers a supported setup — a bare id would only be safe next to an out-of-band provider column.

| Provider          | Source                                | Key                        |
| ----------------- | ------------------------------------- | -------------------------- |
| **Polar**         | `webhook-id` header                   | `polar:<id>`               |
| **Dodo Payments** | `webhook-id` header                   | `dodo-payments:<id>`       |
| **Stripe**        | `id` on the envelope                  | `stripe:evt_…`             |
| **Paddle**        | `event_id` on the envelope            | `paddle:evt_…`             |
| **Lemon Squeezy** | SHA-256 of the raw body               | `lemon-squeezy:sha256:<hex>` |

Two details worth knowing:

- **Paddle's key is `event_id`, not `notification_id`.** The latter identifies one *delivery* — a
  dashboard replay mints a new one — so it would defeat de-duplication entirely.
- **Lemon Squeezy publishes no event id at all**, in headers or body, so the raw body is the only stable
  delivery identity. A redelivery is byte-identical and hashes the same, which is what you need; the cost
  is that two genuinely distinct deliveries with byte-identical bodies would be indistinguishable. Any
  provider whose id is missing falls back to the same `sha256:` form — a Polar or Dodo Payments delivery
  parsed from `{ headers: {}, body }`, for instance — so a derived key is always self-evident in a log.

:::warning
**This dedupes redeliveries of one event. It does not collapse several events describing one change.**
Polar and Dodo Payments fan out: a single activation emits both `subscription.active` and
`subscription.updated`, two distinct events with two distinct keys. Stripe documents the same class of
separate `evt_` ids describing one underlying change. So the key protects you from processing the *same*
event twice — it is not a "one state change, one callback" guarantee. Converge on state (upsert plus the
staleness guard above) rather than assuming each key is a change worth reacting to, and see
[the webhook handler guide](/docs/guides/webhook-handler#3-persist--upsert-by-subscription-id) for the
read-then-upsert race that event-id dedupe *cannot* fix.
:::
