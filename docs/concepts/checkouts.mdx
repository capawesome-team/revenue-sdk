A checkout is the hand-off from your app to the provider's payment page. `checkouts.create` returns a
normalized `Checkout` whose `url` you redirect the customer to; `checkouts.get` reads one back.

## Creating a checkout

```ts
const checkout = await client.checkouts.create({
  items: [{ product: price.checkoutRef, quantity: 1 }],
  customerEmail: 'ada@example.com',
  successUrl: 'https://example.com/thanks',
  metadata: { userId: 'user_123' },
});

redirect(checkout.url);
```

The client validates `items` before any request is made: an empty array, an empty `product` string, or a
`quantity` that isn't a positive integer throws `RevenueError` with code `validation`.

## Items, quantity, and success URL support

| Provider          | Multiple items | `quantity` > 1 | `successUrl`               | `customerId` on create |
| ----------------- | -------------- | -------------- | -------------------------- | ---------------------- |
| **Polar**         | yes            | **no**         | yes                        | yes                    |
| **Lemon Squeezy** | **no** (one)   | yes            | yes (`redirect_url`)       | **no** (use `customerEmail`) |
| **Stripe**        | yes            | yes            | yes                        | yes                    |
| **Paddle**        | yes            | yes            | **no** — see below         | yes (email is resolved to a customer) |
| **Dodo Payments** | yes            | yes            | yes (`return_url`)         | yes                    |

Unsupported combinations throw `RevenueError` with code `unsupported` rather than silently dropping
your input:

- Polar rejects any item `quantity` other than `1`.
- Lemon Squeezy rejects more than one item, and rejects `customerId` (pass `customerEmail` instead).
- Paddle rejects `successUrl` — the client gates this one *before* the request, via the
  `checkoutSuccessUrl` capability.

:::warning
**Paddle has no provider-hosted checkout.** `checkouts.create` creates a *transaction*, and the returned
`checkout.url` points at the **default payment link** configured in your Paddle dashboard — a page you
host yourself that runs [Paddle.js](https://developer.paddle.com/paddlejs/overview) on an approved
domain. Without a configured default payment link and an approved domain, the URL will not work. This
is why Paddle reports `hostedCheckout: false` and `checkoutSuccessUrl: false`: success redirects are
configured in Paddle.js, not in the API call.
:::

Check the capability before offering a success URL in provider-agnostic code:

```ts
await client.checkouts.create({
  items: [{ product: price.checkoutRef }],
  successUrl: client.capabilities.checkoutSuccessUrl
    ? 'https://example.com/thanks'
    : undefined,
});
```

## Checkout expiry

Two of the five providers let you choose when a checkout link stops working; the rest apply a fixed
lifetime. `expiresAt` is a `Date`, gated by the `checkoutExpiresAt` capability:

```ts
await client.checkouts.create({
  items: [{ product: price.checkoutRef }],
  expiresAt: client.capabilities.checkoutExpiresAt
    ? new Date(Date.now() + 60 * 60 * 1000) // one hour
    : undefined,
});
```

| Provider          | `expiresAt` | Behavior                                                                  |
| ----------------- | ----------- | -------------------------------------------------------------------------- |
| **Polar**         | **no**      | Fixed 24 hours, set server-side.                                            |
| **Lemon Squeezy** | yes         | `expires_at`, ISO 8601. Omit it and the link **never** expires.             |
| **Stripe**        | yes         | `expires_at`, unix seconds. Stripe accepts 30 minutes to 24 hours from creation. |
| **Paddle**        | **no**      | Transactions have no expiry field.                                          |
| **Dodo Payments** | **no**      | Fixed 24 hours, or 15 minutes for a confirmed checkout.                     |

The client checks three things before any request:

- `expiresAt` on a provider without `checkoutExpiresAt` → `unsupported`.
- An invalid `Date` (`NaN`) → `validation`.
- A date at or before now → `validation`.

:::note
The SDK deliberately does **not** enforce Stripe's 30-minute-to-24-hour window. It is one provider's rule,
Stripe measures it against its own clock — so near either boundary, clock skew alone would turn a valid
date into a client-side rejection — and clamping the value would silently rewrite what you asked for.
Stripe rejects an out-of-range date itself, and that `400` arrives as a `validation` error like any other.
:::

`Checkout.expiresAt` is the read side of the same field. It is populated on Polar, Lemon Squeezy, and
Stripe — Polar included, which reports the expiry it picked without letting you choose it. Paddle
transactions and Dodo Payments checkout sessions carry no expiry at all, so it stays `undefined` there.

## Metadata propagation

`metadata` is a flat `Record<string, string | number | boolean>`. Where it ends up differs per provider:

| Provider          | Written as                                                    | Reaches the subscription?                       |
| ----------------- | ------------------------------------------------------------- | ----------------------------------------------- |
| **Polar**         | checkout `metadata`                                            | yes — Polar copies it onto the order/subscription |
| **Lemon Squeezy** | `checkout_data.custom`                                         | only via webhooks, as `meta.custom_data`         |
| **Stripe**        | session `metadata` **and** `subscription_data[metadata]`        | yes — the SDK writes both                        |
| **Paddle**        | transaction `custom_data`                                      | yes — carried onto the subscription              |
| **Dodo Payments** | checkout `metadata`                                            | yes                                              |

Two of these deserve attention:

- **Stripe** does *not* copy session metadata onto the created subscription. `revenue-sdk` writes
  `subscription_data[metadata]` as well whenever the checkout is in subscription mode, so
  `subscription.metadata` carries your keys.
- **Lemon Squeezy** never attaches custom data to the subscription resource. It travels only in the
  webhook envelope (`meta.custom_data`), which is why `Subscription.metadata` is populated on Lemon
  Squeezy webhook events but is `undefined` when you fetch the subscription over the API.

:::tip
Treat metadata as a hint, not a source of truth. Store your own mapping from provider
`customerId`/`subscriptionId` to your user, and use metadata only to bootstrap that mapping on first
sight.
:::

## Checkout status semantics

`Checkout.status` is a three-value union plus `null`:

| `status`   | Meaning                                                    |
| ---------- | ---------------------------------------------------------- |
| `open`     | Not paid (yet). The link may still be used.                |
| `complete` | **Paid.** Safe to fulfill.                                 |
| `expired`  | The checkout failed, was canceled, or timed out.           |
| `null`     | The provider exposes no checkout status (Lemon Squeezy).   |

Per-provider mapping:

| Provider          | → `complete`            | → `expired`             | → `open`                                     |
| ----------------- | ----------------------- | ----------------------- | -------------------------------------------- |
| **Polar**         | `succeeded`             | `expired`, `failed`     | everything else                              |
| **Lemon Squeezy** | —                       | —                       | — (`status` is always `null`)                 |
| **Stripe**        | `complete` **and** `payment_status !== 'unpaid'` | `expired` | `open`, **and** `complete` while `payment_status === 'unpaid'` |
| **Paddle**        | `paid`, `completed`     | `canceled`              | everything else                               |
| **Dodo Payments** | `payment_status: succeeded` | `cancelled`, `failed` | everything else                            |

:::warning
**Stripe: `complete` does not mean paid.** With delayed payment methods (bank debits, vouchers) a
session reaches `status: complete` with `payment_status: unpaid`. `revenue-sdk` maps that back to
`open`, so `checkout.status === 'complete'` always means *the money arrived*. Wait for the
`checkout.session.async_payment_succeeded` webhook before fulfilling those.
:::

## Reading a checkout back

```ts
const checkout = await client.checkouts.get({ id: checkoutId });

if (checkout.status === 'complete') {
  // Paid.
}
```

:::note
On **Dodo Payments** the checkout-status endpoint does not return the checkout URL, so a `Checkout`
fetched with `checkouts.get` has `url: ''`. Persist the URL from `checkouts.create` if you need it
later.
:::

## What gets into CreateCheckoutParams

`CreateCheckoutParams` is small on purpose. A field is added when both of these hold:

1. **At least two providers implement the same concept** — not merely a similar-sounding field.
2. **The SDK's own model doesn't structurally prevent it.**

Below that bar, the answer is to call the provider's endpoint directly. `checkouts.create` is a single
POST, and nothing downstream depends on having gone through it: `Checkout.raw`, the webhook path, and
`orders.*` all work the same on a checkout you created yourself.

`expiresAt` cleared the bar on two providers, and `Checkout.expiresAt` already existed on the read side —
it closed an asymmetry rather than introducing a concept. Three requests did not clear it:

- **`embedOrigin`** — one provider out of five, and the rest are not near-misses. Polar's `embed_origin`
  is a security allowlist: the iframe posts the session token only to a listed origin. Lemon Squeezy's
  `checkout_options.embed` is a display toggle with no origin and no security semantics. Stripe has no
  origin allowlist at all — embedding is a second checkout *mode* (`ui_mode` + `client_secret` +
  `return_url`) that forbids `success_url`, so it collides with `checkoutSuccessUrl` and needs a
  `client_secret` field on `Checkout`. That is a design, not a parameter. Paddle approves domains once in
  the dashboard, and Dodo Payments has nothing.
- **A per-checkout product description** — only Lemon Squeezy's `product_options.description` is usable.
  On Stripe it is structurally impossible: `items[].product` is a catalog price ID, `price` and
  `price_data` are mutually exclusive, so overriding the description means abandoning catalog pricing.
  `line_items[].description` does not exist on Checkout Sessions.
- **A `providerOptions` passthrough** — rejected outright, not merely declined. It can't be typed without
  making `RevenueProvider` and `createClient` generic, it would freeze the private per-provider wire
  shapes into the public API, and it voids "throw `unsupported`, never silently drop" by construction:
  the client can't gate keys it doesn't know. It would also collide with the fields the SDK already
  writes — `product_options.redirect_url`, `invoice_creation`, `subscription_data[metadata]`,
  `success_url`.

:::warning
Do not fulfill from the success page alone. The customer may close the tab, and delayed payment methods
settle minutes or hours later. Treat the redirect as a UX signal and fulfill from
[webhooks](/docs/concepts/webhooks) — see the [checkout flow guide](/docs/guides/checkout-flow).
:::
