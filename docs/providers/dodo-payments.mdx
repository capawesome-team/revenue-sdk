Dodo Payments is a merchant of record. Import the factory from `revenue-sdk/dodo-payments`.

```ts
import { createClient } from 'revenue-sdk';
import { dodoPayments } from 'revenue-sdk/dodo-payments';

const client = createClient({
  provider: dodoPayments({ apiKey: process.env.DODO_PAYMENTS_API_KEY! }),
});
```

## Authentication

Create an API key in the Dodo Payments dashboard under **Developer → API keys**. Test and live modes are
**separate hosts** with separate keys and separate catalogs.

## Test mode

```ts
dodoPayments({ apiKey: process.env.DODO_PAYMENTS_TEST_API_KEY!, server: 'test' });
```

## Webhooks

Create the endpoint in the dashboard under **Developer → Webhooks** and copy the signing secret
(`whsec_…`).

```ts
import { parseWebhookEvent, verifyWebhook } from 'revenue-sdk/dodo-payments';

const headers = request.headers;
const body = await request.text();

if (!(await verifyWebhook({ headers, body, secret: env.DODO_PAYMENTS_WEBHOOK_SECRET }))) {
  return new Response('invalid signature', { status: 401 });
}

const event = await parseWebhookEvent({ headers, body });
```

Dodo Payments uses [Standard Webhooks](https://www.standardwebhooks.com/) headers (`webhook-id`,
`webhook-timestamp`, `webhook-signature`) with a 300-second tolerance.

:::warning
Dodo Payments follows the **strict** Standard Webhooks key derivation: the `whsec_` prefix is stripped
and the remainder **base64-decoded** into the HMAC key bytes. Polar sends the same headers but uses its
secret **verbatim**. Copying one implementation to the other fails every signature — pass each provider
its own secret to its own `verifyWebhook`.
:::

Events worth subscribing to: `subscription.active`, `subscription.updated`, `subscription.renewed`,
`subscription.plan_changed`, `subscription.on_hold`, `subscription.paused`, `subscription.cancelled`,
`subscription.expired`, `subscription.failed`, `payment.succeeded`.

:::note
Dodo Payments has **no `subscription.created` event**. The first signal for a new subscription is
`subscription.active`, which also fires after recovery from `on_hold`. Every subscription event
normalizes to `subscription.updated` (or `subscription.canceled`), so **upsert** rather than insert.
:::

## License keys

The `/licenses/*` routes need **no credential**, so validate, activate, and deactivate are standalone
exports rather than client methods — safe to ship inside a desktop, mobile, or CLI app.

```ts
import {
  activateLicenseKey,
  deactivateLicenseKey,
  validateLicenseKey,
} from 'revenue-sdk/dodo-payments';

const { valid } = await validateLicenseKey({
  key: 'LICENSE-KEY',
  activationId: 'ACTIVATION_ID', // optional — narrows the check to one device
});

const activation = await activateLicenseKey({ key: 'LICENSE-KEY', label: 'MacBook Pro' });

await deactivateLicenseKey({ key: 'LICENSE-KEY', activationId: activation.id });
```

## Quirks

- **The product is the purchasable unit.** Dodo prices have no identifier of their own, so
  `Price.id`, `Price.checkoutRef`, and `Product.id` are all the product ID, and each product has at most
  one price.
- **No end-trial operation.** `subscriptions.endTrial` throws `unsupported` (`endTrial: false`).
- **No pause or resume.** Dodo has neither an endpoint nor a paused subscription status, so
  `subscriptions.pause` and `subscriptions.resume` throw `unsupported` (`pause: false`) and
  `pauseAtPeriodEnd` is always `false`.
- **No `prorate` proration.** There is no defer-to-next-invoice mode, only `prorated_immediately` and
  `do_not_bill`. Omitting `prorationBehavior` behaves as `invoice_now`.
- **Unversioned, additive API.** There is no version header and fields are added without notice, so the
  SDK's wire types are tolerant, enums are treated as open, and **ID prefixes are never validated**.
  Unrecognized subscription statuses fall back to `active`.
- **`TimeInterval` is capitalized** (`'Month'`, `'Year'`) — the only enum in the SDK that is. It is
  normalized to the lowercase unified `BillingInterval`.
- **Pagination has no `has_more`.** Lists use zero-based `page_number` with an `{ items }` envelope; the
  SDK stops when a page comes back shorter than the requested size. See
  [Pagination](/docs/concepts/pagination).
- **`POST /checkouts` is the current endpoint.** The legacy `POST /payments` and `POST /subscriptions`
  flows are deprecated and unused.
- **`POST /change-plan` returns 200 with an empty body**, so `subscriptions.changePlan` re-fetches the
  subscription to return its updated state — one extra request.
- **Portal session parameters go in the query string** on a POST
  (`POST /customers/{id}/customer-portal/session?return_url=…`).
- **Usage events require an `event_id`.** `usage.report` posts a one-event batch to `/events/ingest`,
  and Dodo requires an `event_id` to deduplicate on. When `idempotencyKey` is omitted the SDK generates
  a UUID — unique per attempt, so **that call is not replay-safe**. A `timestamp` may be at most **one
  hour** old (and 5 minutes ahead), otherwise the request is rejected with `400`; you cannot backfill.
  An unknown `customer_id` is dropped silently rather than erroring. See
  [Usage-based billing](/docs/concepts/usage-based-billing).
- **`checkouts.get` returns no URL.** The status endpoint omits it, so a `Checkout` read back has
  `url: ''`. Persist the URL from `checkouts.create`.
- **Validate cannot be scoped.** `POST /licenses/validate` answers with literally `{ "valid": boolean }`
  — no product, business, customer, or expiry — so a key from any Dodo Payments merchant for any product
  validates as `true`, and `LicenseKeyValidation.licenseKey` is **always `undefined`**. Only
  `activateLicenseKey` reveals ownership (`business_id` and `product` on `raw`); bind the key to your
  product there, or read it server-side with `client.licenseKeys.get`. See
  [License keys](/docs/concepts/license-keys).
- **Two spellings for the license routes.** The credential-free ones are `/licenses/validate`,
  `/licenses/activate`, `/licenses/deactivate`; the merchant ones are `/license_keys` with an
  **underscore**.
- **The public license routes carry the tightest rate limits** of the three supporting providers —
  roughly 20 requests per second and 100 per minute. Cache the verdict in your app instead of validating
  on every action.
- **The merchant license endpoints are marked `@deprecated` upstream** in favour of an entitlements-based
  replacement, but still function; `client.licenseKeys` continues to use them.
- **A 404 on validate is a verdict, not an error.** An unknown key answers `200 { "valid": false }` in
  most cases and `404` in others, so the SDK maps both to `valid: false`. `activateLicenseKey` on an
  unknown key still throws `not_found`, and `deactivateLicenseKey` answers `200` with an empty body.
