Polar is a merchant of record for digital products. Import the factory from `revenue-sdk/polar`.

```ts
import { createClient } from 'revenue-sdk';
import { polar } from 'revenue-sdk/polar';

const client = createClient({
  provider: polar({ accessToken: process.env.POLAR_ACCESS_TOKEN! }),
});
```

## Authentication

Create an **organization access token** in the Polar dashboard under **Settings → Developers → Access
tokens**. Organization tokens are scoped to a single organization, which is why the factory needs no
organization ID.

```ts
polar({ accessToken: process.env.POLAR_ACCESS_TOKEN! });
```

Grant the token the scopes for what you use: products, checkouts, customers, subscriptions, and
customer sessions.

## Sandbox

Polar's sandbox is a **separate environment on a separate host** (`sandbox-api.polar.sh`) with its own
organization, its own products, and its own tokens — a production token will not authenticate against
it.

```ts
polar({
  accessToken: process.env.POLAR_SANDBOX_ACCESS_TOKEN!,
  server: 'sandbox',
});
```

## Webhooks

Create the endpoint in the Polar dashboard under **Settings → Webhooks**, choose the **Raw** payload
format, and copy the generated signing secret.

```ts
import { parseWebhookEvent, verifyWebhook } from 'revenue-sdk/polar';

const headers = request.headers;
const body = await request.text();

if (!(await verifyWebhook({ headers, body, secret: env.POLAR_WEBHOOK_SECRET }))) {
  return new Response('invalid signature', { status: 401 });
}

const event = await parseWebhookEvent({ headers, body });
```

Polar uses [Standard Webhooks](https://www.standardwebhooks.com/) headers (`webhook-id`,
`webhook-timestamp`, `webhook-signature`) with a 300-second timestamp tolerance. The signing secret is
used **verbatim, including its `whsec_` prefix** — do not strip or base64-decode it.

Events worth subscribing to: `subscription.created`, `subscription.updated`, `subscription.active`,
`subscription.canceled`, `subscription.uncanceled`, `subscription.revoked`, `subscription.cycled`,
`order.paid`, `checkout.updated`.

:::warning
Polar emits `subscription.canceled` when a cancellation is merely **scheduled**; the terminal event is
`subscription.revoked`. `revenue-sdk` normalizes them to `subscription.updated` and
`subscription.canceled` respectively — see [Webhooks](/docs/concepts/webhooks).
:::

## License keys

Validating, activating, and deactivating a key needs **no credential**, so those three functions are
standalone exports rather than client methods — safe to ship inside a desktop, mobile, or CLI app.

```ts
import { activateLicenseKey, deactivateLicenseKey, validateLicenseKey } from 'revenue-sdk/polar';

const { valid, licenseKey } = await validateLicenseKey({
  key: 'POLAR-KEY-0001',
  organizationId: 'ORGANIZATION_ID',
  activationId: 'ACTIVATION_ID', // optional — narrows the check to one device
});

const activation = await activateLicenseKey({
  key: 'POLAR-KEY-0001',
  organizationId: 'ORGANIZATION_ID',
  label: 'MacBook Pro',
});

await deactivateLicenseKey({
  key: 'POLAR-KEY-0001',
  organizationId: 'ORGANIZATION_ID',
  activationId: activation.id,
});
```

Merchant-side management — `client.licenseKeys.list/listAll/get/update` — does need the access token and
reads `/v1/license-keys`. See [License keys](/docs/concepts/license-keys).

## Quirks

- **A `Product` is a Polar product**, and `Price.checkoutRef` is the **product ID** — Polar checkouts
  take `products: string[]`, not price IDs.
- **No item quantities.** A checkout item with `quantity` other than `1` throws `unsupported`; so does a
  plan change with a quantity.
- **No `none` proration.** Polar's `next_period` defers the plan change itself and `reset` restarts the
  billing anchor — neither means "switch now, bill nothing extra", so the SDK refuses rather than pick a
  lookalike.
- **Pause is period-end only.** `subscriptions.pause({ behavior: 'immediately' })` throws `unsupported`;
  the pause is scheduled, so `status` stays unchanged and `pauseAtPeriodEnd` becomes `true` until it
  takes effect. A `resumesAt` must fall **after** the current period end.
- **Resume takes effect immediately.** `subscriptions.resume` starts a new billing period and charges
  the customer — it is not a "continue where we left off" operation.
- **Trailing slashes are load-bearing.** Collection routes are `/v1/checkouts/`, `/v1/products/`,
  `/v1/customers/` — the SDK sends them exactly as Polar requires. Relevant if you pass a custom
  `baseUrl`.
- **`external_customer_id`** links your own user IDs to Polar customers; it lives on the raw payload.
  Event ingestion accepts it as an alternative customer key, but `usage.report` always sends the Polar
  customer ID — external keying needs Polar's native API.
- **No idempotency keys**, apart from event ingestion. Polar's REST API has none, so retrying a
  `checkouts.create` may create a second checkout. The client's rate-limit retry never applies to writes
  that could duplicate a charge.
- **Usage ingestion is batch-only and deduplicated permanently.** `usage.report` posts a one-event batch
  to `/v1/events/ingest`, and `idempotencyKey` becomes the event's `external_id` — Polar enforces it with
  a permanent unique index, so replaying the same key is safe. A backdated `timestamp` is accepted, but
  events are attributed to billing periods by **receipt time** and Polar never issues a retroactive
  invoice, so backdating affects reporting only. `metadata` is capped at 50 pairs, keys at 40 characters
  and string values at 500. See [Usage-based billing](/docs/concepts/usage-based-billing).
- **Meters are returned inline on the subscription.** Polar is the only provider that populates
  `Subscription.meters` with the current period's consumed units, credited units, and accrued amount.
- **License validation must be unauthenticated.** The customer-portal license routes answer
  `401 invalid_token` when **any** `Authorization` header is present, which is why `validateLicenseKey`,
  `activateLicenseKey`, and `deactivateLicenseKey` are standalone subpath exports that send no
  credential. `organizationId` takes the place of the credential and is a public identifier.
- **A 404 from validate means every kind of rejection** — unknown key, revoked, disabled, expired, or an
  activation that doesn't match. The SDK maps it to `valid: false` instead of throwing; any other error
  status still throws.
- **Activate returns 403 for two different reasons**: the activation limit is reached, *or* the key has
  no activation limit configured at all. Both surface as `RevenueError { code: 'forbidden' }`.
- **`LicenseKey.productId` is never set.** A Polar key hangs off a *benefit*, not a product — `raw`
  carries `benefit_id`, and a benefit ID is not something `products.get` accepts.
- **`activationCount` only comes from `licenseKeys.get`.** The list and PATCH responses carry no
  `activations` array, so the field stays `undefined` there.
- **`update({ disabled: true })` writes Polar's `disabled` status, not `revoked`.** `revoked` belongs to
  Polar's benefit lifecycle and is flipped back to `granted` on the next grant cycle; `disabled` is the
  merchant switch Polar never touches. `disabled: false` writes `granted`.
- **No `expired` license status.** Expiry lives only in `expires_at`, so the SDK derives
  `status: 'expired'` from it. Polar rejects expired keys server-side on validate, so a validation
  verdict can never contradict the derivation.
- **`Retry-After` on 429**, so the client's bounded rate-limit retry works out of the box.
- **Trial length** is normalized to `Price.trialDays` only for day- and week-based trials; month- and
  year-based trials have no exact day count and are left `undefined` — read `raw`.
