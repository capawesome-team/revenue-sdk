Lemon Squeezy is a merchant of record for digital products. Import the factory from
`revenue-sdk/lemon-squeezy`.

```ts
import { createClient } from 'revenue-sdk';
import { lemonSqueezy } from 'revenue-sdk/lemon-squeezy';

const client = createClient({
  provider: lemonSqueezy({
    apiKey: process.env.LEMON_SQUEEZY_API_KEY!,
    storeId: process.env.LEMON_SQUEEZY_STORE_ID!,
  }),
});
```

## Authentication

Create an API key in the Lemon Squeezy dashboard under **Settings → API**. `storeId` is required — a
checkout must name the store it belongs to, and customer/subscription lists are scoped to it. You'll
find the numeric store ID in **Settings → Stores** or via `GET /v1/stores`.

## Test mode

Test mode is a **property of the API key**, not a flag on the request: a key created while the store is
in test mode talks to test data, a live key talks to live data. There is no `server` option — swap the
key (and the matching `storeId`) via environment variables.

## Webhooks

Create the endpoint in **Settings → Webhooks**, pick the events, and copy the **signing secret** you
entered there.

```ts
import { parseWebhookEvent, verifyWebhook } from 'revenue-sdk/lemon-squeezy';

const headers = request.headers;
const body = await request.text();

if (!(await verifyWebhook({ headers, body, secret: env.LEMON_SQUEEZY_WEBHOOK_SECRET }))) {
  return new Response('invalid signature', { status: 401 });
}

const event = await parseWebhookEvent({ headers, body });
```

The `X-Signature` header carries a hex HMAC-SHA256 of the raw body, keyed by the secret used verbatim.
There is **no timestamp**, so there is no replay window to enforce — de-duplicate on your side.

Events worth subscribing to: `subscription_created`, `subscription_updated`, `subscription_cancelled`,
`subscription_resumed`, `subscription_paused`, `subscription_unpaused`, `subscription_expired`,
`order_created`, `subscription_payment_success`, and — if you sell license keys — `license_key_created`.

:::note
Checkout custom data arrives **only** in `meta.custom_data` on the webhook envelope, never on the
resource. This is the only place `Subscription.metadata` gets populated on Lemon Squeezy.
:::

## License keys

The public license API needs **no credential**, so validate, activate, and deactivate are standalone
exports rather than client methods — safe to ship inside a desktop, mobile, or CLI app.

```ts
import {
  activateLicenseKey,
  deactivateLicenseKey,
  validateLicenseKey,
} from 'revenue-sdk/lemon-squeezy';

const expect = { storeId: 76833, variantId: 1615641 };

const validation = await validateLicenseKey({ key: 'LICENSE-KEY', expect });
const activated = await activateLicenseKey({ key: 'LICENSE-KEY', expect, label: 'MacBook Pro' });
await deactivateLicenseKey({ key: 'LICENSE-KEY', expect, activationId: activated.id });
```

Return types match the other subpaths: `validateLicenseKey` resolves to a `LicenseKeyValidation`,
`activateLicenseKey` to a `LicenseKeyActivation`, `deactivateLicenseKey` to `void`. Lemon Squeezy
answers all three routes with one envelope, so the SDK normalizes it away. Because activation and
deactivation report their outcome through the return type alone, a refusal throws rather than
returning a false verdict — a reached activation limit surfaces as `validation`, and a key belonging
to another store as `not_found`. Only `validateLicenseKey` reports a rejection as `valid: false`.

Merchant-side management — `client.licenseKeys.list/listAll/get/update` — uses the API key and reads
`/v1/license-keys`, filtered by the factory's `storeId`. See
[License keys](/docs/concepts/license-keys).

## Orders

Lemon Squeezy has no single payments collection, so a unified `Order` is the **union of an Order and a
Subscription Invoice**. A one-off purchase raises an order; a renewal raises an invoice and no order;
the **first** subscription payment raises **both** — the same money under two IDs, in two numeric ID
spaces, with nothing joining them.

`orders.list` therefore returns **all orders, plus every subscription invoice whose `billing_reason` is
not `initial`**, which yields each payment exactly once. Both requests are scoped to the factory's
`storeId`.

:::warning
**Pages are not chronological.** The cursor drains `/v1/orders` first and only then starts on
`/v1/subscription-invoices`, so an old purchase can precede yesterday's renewal. Every other provider
returns newest-first — sort by `createdAt` after draining `listAll` if you need strict chronology.
:::

- **A page can come back short, or empty.** The `initial` invoices are dropped after Lemon Squeezy has
  already paged, and the page is never backfilled. Follow the cursor until it is `undefined`.
- **`orders.get` tries both ID spaces.** It reads `/v1/orders/{id}` and falls back to
  `/v1/subscription-invoices/{id}` on a `not_found`; if both miss, the order lookup's `not_found` is
  what surfaces. The fallback costs a second request whenever the ID is an invoice.
- **No customer filter.** `/v1/orders` filters by store, user email, and order number only, so
  `listOrdersByCustomer` is `false` and `orders.list({ customerId })` throws `unsupported`. Listing
  unfiltered works.
- **`subscriptionId` is only ever set on the invoice half** — a Lemon Squeezy order carries no
  subscription reference.
- **`refundStatus` is derived from amounts.** The `refunded` boolean means *fully* refunded only, so it
  is deliberately not read; the SDK compares `refunded_amount` against `total` (and treats status
  `refunded` as full).
- **Invoice URLs do not expire.** `getInvoiceUrl` returns `urls.receipt` for an order and
  `urls.invoice_url` for a subscription invoice — both hosted by Lemon Squeezy. A subscription invoice
  that is still pending has no PDF link yet and throws `not_found`.
- **`void` belongs to invoices only.** It is a bill cancelled while the subscription was paused; orders
  never carry it.

See [Orders](/docs/concepts/orders) for the model and the cross-provider comparison.

## Quirks

- **A `Product` is a Lemon Squeezy VARIANT.** The variant is the purchasable unit, so
  `Product.id` and `Price.checkoutRef` are both the variant ID, and every product has exactly one price.
- **Numeric IDs coerced to strings.** JSON:API puts `data.id` as a string but foreign keys inside
  `attributes` as numbers. The SDK coerces everything with `String()`, so `customerId`, `productId`, and
  `priceId` are always strings.
- **The current price comes from `price-model`.** `/v1/prices?filter[variant_id]=…` is an append-only
  price *history*; the SDK reads the variant's `price-model` relationship instead.
- **JSON:API content type on every request**, including GETs (`application/vnd.api+json`).
- **Empty objects serialize as `[]`.** Lemon Squeezy returns `[]` where an empty object is expected
  (`custom`, `billing_address`); the mappers tolerate it.
- **One item per checkout, and no `customerId`.** More than one item throws `unsupported`; attaching an
  existing customer throws `unsupported` — pass `customerEmail` instead. Quantities above `1` are
  supported (via `variant_quantities`).
- **No cancellation reasons**, and **no immediate revoke** — `subscriptions.cancel` always runs to the
  end of the period. `subscriptions.revoke` throws `unsupported`.
- **Cannot filter subscriptions by customer.** `subscriptions.list({ customerId })` throws
  `unsupported`; Lemon Squeezy filters by store, product, variant, or email.
- **`cancelled` is not terminal.** It means "grace period until `ends_at`, still resumable", so it maps
  to `active` + `cancelAtPeriodEnd: true`. The terminal status is `expired`.
- **Portal and update-payment-method URLs expire after 24 hours**, so the SDK fetches them on demand.
  A customer without a subscription has no portal and throws `not_found`. `returnUrl` is unsupported.
- **Pause is immediate and voids invoices.** Lemon Squeezy cannot schedule a pause, so
  `subscriptions.pause({ behavior: 'period_end' })` throws `unsupported` and `pauseAtPeriodEnd` is always
  `false`. The SDK fixes Lemon Squeezy's pause `mode` to `void`, which voids the invoices raised while
  the subscription is paused; the alternative `free` mode is not exposed.
- **No usage reporting.** `usage.report` throws `unsupported`. `POST /v1/usage-records` exists, but it
  keys on a **subscription-item ID** rather than a customer — an extra lookup that is ambiguous as soon
  as a customer has several subscriptions — and it has no idempotency at all with `increment` semantics,
  so a single replay double-bills. See [Usage-based billing](/docs/concepts/usage-based-billing).
- **The public license API is unscoped, so `expect` is required.** It takes only the key, which means
  *any* Lemon Squeezy merchant's key validates against it. The SDK asserts `expect` against the response
  `meta` on all three calls; a foreign key comes back `valid: false` with `licenseKey` and `activation`
  left `undefined`, and a response without `meta` fails closed. See
  [License keys](/docs/concepts/license-keys).
- **Test and live keys share one host.** Unlike the merchant API, the license API is not scoped by an
  API key, so a test-mode key validates against production. `license_key.test_mode` on `raw` is the only
  discriminator — check it if you ship test keys.
- **A non-OK response can still be a verdict.** Activate answers
  `400 {"activated":false,"error":"License key activation limit reached."}`, and an unknown key answers
  `404 {"valid":false,…}`. Any 4XX carrying the verdict field is returned as `valid: false`; anything
  else re-throws as a `RevenueError`.
- **`LicenseKey.productId` depends on the path.** On merchant reads it is `undefined`: Lemon Squeezy's
  `product_id` names the LS *product*, while the unified `Product` is a *variant*, so the ID would not
  work with `products.get`. On the public license path the SDK reports `meta.variant_id` instead.
- **`disabled` arrives as a boolean or a number** depending on the endpoint; any truthy value maps to
  `status: 'disabled'`.
- **PayPal subscriptions ignore `PATCH /subscriptions`** — Lemon Squeezy silently no-ops. Plan changes,
  uncancel, pause, and resume therefore do nothing for PayPal-paid subscriptions; re-read the
  subscription and check before reporting success to the customer.
