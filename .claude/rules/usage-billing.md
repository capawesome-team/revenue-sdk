# Usage-based billing (decided — do not relitigate)

`client.usage.report({ events, signal? }) → Promise<void>`, where each `UsageEvent` is `{ customerId, eventName, value?, metadata?, idempotencyKey?, timestamp? }`. One list means ONE provider call: a job that reports one event per customer makes one request, not one per event. `customerId` is the PROVIDER's customer ID. `eventName` must match the meter config EXACTLY (case-sensitive). `value` is shorthand for a `value` entry in the event properties (the default aggregation key), and an explicit `value` beats `metadata.value`. The fold happens once per event in `providers/shared.ts` (`toUsagePayload(event)`). Client order: (1) validate EVERY event: non-empty `customerId`/`eventName`, finite `value` AND every numeric `metadata` entry (`validation`, the message names `events[i].<field>`). Meters aggregate on a caller-configured key, so any number can be the billed quantity. (2) Gate on `usageReporting` (`unsupported`). (3) Gate a list longer than one on `usageBatchReporting` (`unsupported`). (4) Return WITHOUT a request for an empty list. (5) Call `reportUsage` once. It **NEVER retries**: a replayed event only dedupes when the caller passed `idempotencyKey`, so an automatic retry would over-bill. The SDK NEVER splits a list. Provider limits (Dodo takes 1,000 events per call) stay with the caller. `usageBatchReporting` and then `usageReporting` sort LAST in `RevenueCapabilities` (after `uncancel`, alphabetical like every other key). `usageReporting`: Polar/Stripe/Dodo `true`, LS/Paddle `false`. `usageBatchReporting`: Polar/Dodo `true`, Stripe/LS/Paddle `false`. Testing: `true` for both.

| Provider | Endpoint                        | Customer key                  | List per call                                                                          | Idempotency                                                                                                     | Backdating                                                                                    |
| -------- | ------------------------------- | ----------------------------- | -------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------- |
| Polar    | `POST /v1/events/ingest`        | `customer_id`                 | whole list in one request                                                              | `external_id`, permanent unique index → replay-safe                                                             | any past ts, but periods attributed by RECEIPT time, no retroactive invoices → reporting only |
| Stripe   | `POST /v1/billing/meter_events` | `payload[stripe_customer_id]` | ONE event per request → `usageBatchReporting: false`, adapter throws `unsupported` too | `identifier`, rolling ≥24h                                                                                      | 35 days past / 5 min future, else error                                                       |
| Dodo     | `POST /events/ingest`           | `customer_id`                 | whole list in one request, max 1,000 events, NOT split by the SDK                      | `event_id` REQUIRED → SDK generates a UUID per event without `idempotencyKey`, so THAT event is not replay-safe | 1 hour past / 5 min future, else 400 — cannot backfill                                        |

Stripe: **2xx ≠ recorded** — meter events validate synchronously, process asynchronously; an unknown customer or an `event_name` with no matching meter is dropped silently and only surfaces via the `v1.billing.meter.error_report_triggered` / `v1.billing.meter.no_meter_found` thin webhooks (not parsed here). `stripe_customer_id`/`value` are the meter's DEFAULT payload keys (`customer_mapping.event_payload_key` / `value_settings.event_payload_key`) → a meter with custom keys needs them in `metadata`. 1,000 events/s but only ONE concurrent call per customer per meter. The v2 meter event stream (`https://meter-events.stripe.com/v2/billing/meter_event_stream`) takes up to 100 events per request, but it first needs a meter event session token from a separate request, and that token is valid for 15 minutes (verified in Stripe's docs on 2026-11-24). So it is not one request either. The SDK does not use it, and `usageBatchReporting` stays `false` for Stripe.

Polar (verified in the Polar sandbox on 2026-11-24): the whole list is checked first. A list with one event for an unknown customer was refused with 422 (→ `validation`) and none of its events was stored. An event sent again with the same `external_id` got 200 and was counted as a duplicate, not stored twice.

LS is off because `POST /v1/usage-records` keys on a subscription-ITEM id (extra lookup, ambiguous with several subscriptions) and has no idempotency at all with `increment` semantics → any replay double-bills. Paddle is off because it has no usage API (Paddle's guidance: meter externally, bill via `POST /subscriptions/{id}/charge`).

`SubscriptionMeter { id, name, consumedUnits, creditedUnits, amount, raw }` on `Subscription.meters?` — **Polar only** (returned inline on the subscription), absent everywhere else; `amount` is minor units accrued so far this period. Testing provider records `state.usageEvents: InMemoryUsageEvent[]`, one entry per event (`payload` = metadata with `value` merged in).

Out of scope (deliberate): meter CRUD/management, reading usage back (`getCurrent` — Polar answers inline, Stripe needs meter id + minute-aligned window keyed on customer+meter, Dodo only returns CLOSED cycles), normalized `Price.amount` for metered/tiered (stays `null`), splitting a list to fit a provider limit, tier tables, seat management.
