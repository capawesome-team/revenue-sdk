# Lemon Squeezy quirks

JSON:API (`application/vnd.api+json` on ALL requests incl. GET). `data.id` is string but FKs in `attributes` are numbers → coerce with `String()`. Empty objects serialize as `[]` (`custom`, `billing_address`). Unified `Product` = LS **variant**; current price via variant `price-model` relationship (NOT `/v1/prices?filter[variant_id]` — that's append-only history). `listProducts` sends `filter[status]=published` (drafts/pending are unbuyable); `/v1/variants` has NO store filter upstream, so a multi-store key lists every store's variants — documented as a limitation, NOT worked around with a products-join. Portal/update URLs expire in 24h — fetch on demand. PayPal subscriptions: `PATCH /subscriptions` silently no-ops (plan change, uncancel, pause, resume AND end-trial — all five go through `patchSubscription`), so the adapter reads `payment_processor` off the PATCH RESPONSE (free — the response IS the subscription) and throws `unsupported` instead of returning an object claiming a mutation happened; `cancel` is a bodyless `DELETE` with no PayPal caveat and is deliberately NOT guarded. `endTrial` sends `billing_anchor: null` — LS documents it as "reset the billing anchor to the current date. Doing this will also remove an active trial", the ONLY documented lever; the reset is unconditional, so on a non-trialing subscription it would silently move the billing day → `endSubscriptionTrial` preflights `GET /v1/subscriptions/{id}` (shared `fetchSubscription` helper, same read `getSubscription` does) and throws `validation` unless the RAW status is `on_trial`; only then is the PATCH sent (the PayPal no-op guard still runs on the PATCH response). `trial_ends_at` is writable but upstream only describes it as adjusting a trial's DURATION and documents nothing for past/present values — do not switch to it without a live test. Webhook **`subscription_resumed` means un-CANCEL** — un-pause is `subscription_unpaused`. `subscription_payment_success` with `billing_reason === 'initial'` → `unknown` (the `order_created` for the same money wins). Pause is `{ pause: { mode: 'void', resumes_at } }`, resume is `{ pause: null }`. No usage reporting (`usageReporting: false`) — `usage-records` keys on a subscription item and has no idempotency. Test mode is a property of the API key. `storeId` required in factory (checkout `store` relationship). Checkout `custom_price` (cents) is the `customAmount` wire field — a SIBLING of `checkout_data`/`product_options` in `attributes`, never nested inside them; on a subscription it prices every renewal until the variant changes. Customer create requires BOTH `name` and `email` and takes the store as a JSON:API relationship (so new customers always land in the factory's store); the customer object has NO metadata/custom-data field at all → `createCustomer`/`updateCustomer` throw `unsupported` when `metadata` is passed. Its `status` doubles as an email-marketing state (`archived` etc.) and is deliberately not exposed. The public license API (`/v1/licenses/*`) is NOT JSON:API — form-encoded body, `Accept: application/json`, own `HttpClient` — and is unscoped, hence the required `expect`; test and live share ONE host, so `license_key.test_mode` on `raw` is the only discriminator (a test key validates against production); non-OK responses that carry the verdict field are verdicts, not errors (activate limit reached = **400** `{"activated":false,"error":"License key activation limit reached."}`), anything else re-throws; merchant `LicenseKey.productId` is undefined (LS `product_id` = LS PRODUCT, unified `Product` = variant → the ID would not work with `products.get`), the public path uses `meta.variant_id` instead; `disabled` arrives as boolean OR number depending on the endpoint.
